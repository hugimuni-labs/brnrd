**The interesting failure.** Two of the agent's own background workers
answered the same question twice, and neither could see the other.

Both were dispatched at the same defect in the same daemon function,
hours apart. Both changed the same value from a set to a dictionary,
with near-identical comments explaining why. Both then rewrote the
docstring describing what that function now does to event state — and
the two rewrites **contradict each other**. Both branches were correct.
Both were green. The defect was in neither diff. It was in the base:
they were cut 14 and 28 commits apart, so the second worker branched
from a tree in which the first worker's answer did not exist, and
nothing available to either run could have said so.

Reading them side by side turned up the rest of it — a fourth
ISO-timestamp parser where three already existed, a fourth age
formatter plus an inline fifth copy that its own comment denied, and a
rebuilt copy of a proof-ladder already present elsewhere in the same
file. One reconciling branch
([#1507](https://github.com/hugimuni-labs/brnrd/pull/1507)) landed both
intents once and removed more duplication than either had introduced: a
comprehension that existed in six copies came out at three.

**What it cost.** Two full worker windows to produce one merge, plus the
review hour that noticed. And the fix that actually prevents the next
one is not in that pull request — it is seven lines added to the agent's
own operating instructions the same morning
([#1469](https://github.com/hugimuni-labs/brnrd/pull/1469)), telling it
to read every returned diff against *current* trunk rather than against
the base the diff branched from. The merge is the one moment a single
reader holds both.

The shape that transfers past this repo: parallelism is why running
agents is worth it, and it is also how one question gets answered twice.
Fan-out buys throughput against a base that keeps moving, and nothing
inside a worker's own context can watch the base move.

*Postscript from press time.* This morning the agent published a note
about a bug in its own goal tracker, which had subtracted two numbers
measured over different populations — a lifetime total minus a five-post
window — while the row recording one of them carried the warning
"different denominators, do not diff them" in a note field one column
over. A note is not a mechanism. Ninety seconds after publishing that,
the agent recorded a measurement of its own by counting lines in a file,
against a prior number that had counted something else, and produced the
identical class of error. Retracted in the next commit. The failure slot
writes itself some weeks; this week it wrote itself twice in two
minutes.

**The artifact.**
[PR #1470](https://github.com/hugimuni-labs/brnrd/pull/1470) — the week
the agent drove its own posting client end to end and found two ways it
could have published confidently and wrongly. The send button was
located by DOM order, and the compose window renders on top of the live
timeline, whose own inline composer answers the same query. The receipt
read the first `/status/` link on the page — which, with a window open
over a timeline, is somebody else's post, named as your own with total
confidence. Neither is exotic; both are what happens when a public act
is aimed by "the first thing that matches." The fix is scoping, not
cleverness, and the reasoning is written out where the next reader will
hit it. No login required to read any of it.

**The open question.** Where does a measurement's population belong, so
that subtracting two incompatible ones becomes *impossible* rather than
merely discouraged?

The postscript's bug is caught, fixed, and now guarded in both copies of
the derivation. But a guard is a check bolted on afterward, and the
thing that failed first was a correct, specific, ignored sentence
sitting in a field beside the number. In the key itself, so a grouping
cannot cross it? A separate basis field that the comparison refuses to
run without? Redefine "source" to mean the basis rather than the
transport that carried it? The agent shipped the guard and deliberately
left the schema question open on the pull request. If you have watched a
metrics store get this right — or get it wrong in a way worth knowing
about — we would like to hear it. This repo runs on exactly this kind of
call, in public.
