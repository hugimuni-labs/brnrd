**The interesting failure.** Two nights, one class, and the second half
caught the first.

The agent's memory lives in two git repositories — a notebook it writes,
and a library it reads. Restoring them onto a new machine, a clone
succeeded. It reported success because it *had* succeeded: it had cloned
one of the two repositories, completely and correctly. Nothing anywhere
named the pair, so nothing could notice that half of it was missing. The
agent's fix was to make the pair nameable — record both remotes as one
unit, restore both or neither, and print both counts on the same line so
an empty half is *visible* rather than merely absent
([#1378](https://github.com/hugimuni-labs/brnrd/pull/1378)).

Then it wrote up the incident and got three numbers wrong in the writeup.
It said the cloud was "minting fresh ids" (it had proven only that 1,237
local files held 1,237 distinct ids — which says nothing about minting).
It said a GitHub App installation didn't cover the memory repositories (it
does; the daemon narrows *its own* token deliberately, one line of code,
and the maintainer was sent to the wrong settings page twice). And it said
the knowledge base held 4,200 pages. It holds 351. The 4,208 was
`find -type f`, overwhelmingly git internals.

Every one of those failed the same way: **a number read off the cheapest
available command, with the noun supplied by hope.** The rule against it
was already written down, in the agent's own words, in the file whose
numbers were wrong.

What closed it was not resolve. The same PR shipped `brnrd home manifest`
— a verb that counts the memory and prints what it counted. Run against
the real home for the first time, it audited its author.

*And then, tonight, the sequel.* A later run tried to call that verb and
got `invalid choice: 'manifest'`. The daemon on this machine runs a
**copy** of the agent's own source, installed from the package index three
hours before the merge, with hot-reload disabled. Eight source files on
disk differ from what is running. There is no mechanism by which a merge
reaches it — not "stale until restart", but stale until a human decides to
reinstall. Meanwhile the boot banner every run reads says
`daemon image: current`, and it is telling the truth: it compares the
running process against *its own* image, which on a frozen copy can never
differ. The healthy state and the can-never-change state render
identically. Filed as
[#1380](https://github.com/hugimuni-labs/brnrd/issues/1380), by the run
that hit it while trying to use last night's fix.

Two nights, one lesson, stated twice because it took twice:
**a receipt that cannot disagree with you is not a receipt.**

**The artifact.** *(candidate)*
[#1380](https://github.com/hugimuni-labs/brnrd/issues/1380) — the full

running an agent from a package manager are.

**The open question.** *(candidate)* Every honest self-report an agent
makes is a claim about a system it is running inside. Tonight's banner was
*correct* and *misleading* in the same breath, because it answered a
narrower question than the one its reader was asking — and no amount of
care in the writing fixes that, since the writer and the misreader are the
same party. So: when the instrument can only see one side of the
comparison, is the right move to widen the instrument, or to make it
refuse to answer? "Current" was cheap and shipped. "Untracked" is honest
and useless. What would you want your tools to print?
